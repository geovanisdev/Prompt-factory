0001 — Bancada single-user local-first, com o caminho multi-tenant desenhado

ADR: 0001 Status: aceita Data: 2026-08-13 Relação: —

Links canônicos: CLAUDE.md (seção Bancada) · src/prompt_factory/annotate/db.py (schema v7, TRANSICOES, vocabulário fechado) · docs/artefatos/prd-padrao-ouro.html (requisito R27) · auditoria de portfólio de 2026-08-13 (artifact privado, Camada 4 do roadmap)

Decisão

A Bancada permanece single-user, local-first, sobre SQLite — e o caminho para multiusuário fica registrado neste documento em vez de implementado: Postgres com isolamento por projeto, autenticação OIDC, RBAC real e claim transacional, a construir apenas quando existir um segundo usuário de verdade. Adotado porque o produto atual é demonstração de método (portfólio de operações e QC de anotação), e cada camada de infraestrutura sem usuário real seria custo sem evidência — enquanto a pergunta "isso escala?" merece resposta escrita, não improvisada.

Consequências

O que fica mais fácil. O produto local continua exatamente como está — nenhuma linha muda por causa deste ADR. A resposta de escala passa a existir por escrito, com os trade-offs nomeados, e qualquer avaliador pode conferi-la contra o código.

O que este ADR impõe: os seis invariantes de migração. O desenho abaixo só é barato enquanto estes invariantes — todos já em vigor no schema v7 — forem preservados por qualquer mudança futura:

#InvariantePor que a migração depende dele
1A máquina de status é dado (db.TRANSICOES), não uma sequência de ifMigra como INSERT numa tabela de transições; reescrevê-la em código de aplicação obrigaria a portar lógica, não dados
2Instrumento, diretriz e brief versionados e pinados por anotação (versao_diretriz, versao_brief, payload_schema)Nenhum passe de migração pode "achatar" versões: a trilha de auditoria responde sob qual regra cada item foi anotado — achatar apagaria a resposta
3Evento gravado na mesma transação da mudança que registraEm Postgres isso continua verdade de graça; quebrá-lo (fila de eventos assíncrona) faria a trilha mentir exatamente nos casos interessantes
4Cruzamento corpus↔anotação por uid, nunca por rowid/idO corpus troca por swap de arquivo e os ids renascem a cada carga; o uid é a única chave estável entre os dois bancos — em qualquer motor
5Vocabulário fechado espelhado banco↔API (cada CHECK sai de uma tupla Python que o Pydantic também valida)Em Postgres os CHECKs viram ENUM ou CHECK — a fonte única em código é o que impede as duas pontas de divergirem na migração
6Sinal único de anotação sintética: gabarito_avaliacao_json IS NOT NULLToda métrica, export e política de entrega deriva dele; uma segunda marca criada "de passagem" na migração produziria duas verdades

O mapa técnico do caminho (quando houver demanda): o claim sob BEGIN IMMEDIATE vira SELECT … FOR UPDATE SKIP LOCKED; a expiração preguiçosa (UPDATE antes de cada claim/listagem) migra sem thread de fundo; os papéis atuais — hoje teatro de autorização declarado na tela — viram RBAC com OIDC, mantendo o servidor como única autoridade sobre o papel; o carimbo de tempo strftime('%Y-%m-%dT%H:%M:%fZ','now') vira now() UTC no mesmo formato lexicograficamente ordenável (a comparação de prazo depende disso); isolamento por projeto via RLS (row-level security) com projeto_id já presente nas tabelas; dados migram por export/import lógico preservando ids e o histórico de eventos.

O que não pode ser revertido sem novo ADR. A honestidade do modo atual: os papéis sem senha existem declarados como demonstração na própria tela. Remover a declaração sem instalar autenticação real seria transformar uma limitação honesta numa mentira de interface.

Custo assumido. Este ADR envelhece com o schema — foi escrito contra a v7. Cada bump de schema que tocar claim, papéis, versionamento de instrumento ou eventos deve reler a tabela de invariantes e, se algum cair, substituir este ADR em vez de remendá-lo.

O que é isto, em 30 segundos

A Bancada é a plataforma de anotação deste projeto — hoje ela roda inteira no computador de uma pessoa só, sem senha e sem servidor na internet. Este documento decide, por escrito, que ela vai continuar assim por enquanto — e desenha, passo a passo, como ela viraria um sistema para muitas pessoas (com banco de dados de servidor, login e permissões) no dia em que isso for necessário. Importa para quem avalia o projeto e pergunta "e se cem pessoas usassem isso ao mesmo tempo?".

The Bancada is this project's annotation platform — today it runs entirely on one person's computer, with no passwords and no internet server. This document decides, in writing, that it will stay that way for now — and lays out, step by step, how it would become a system for many people (with a server database, login, and permissions) the day that becomes necessary. It matters to anyone evaluating the project who asks "what if a hundred people used this at once?".

Por que isto existe

Uma auditoria do projeto (13 de agosto de 2026) apontou um risco de narrativa: chamar a Bancada de "plataforma" sem saber explicar como ela cresceria pode soar como promessa vazia numa entrevista. Construir a versão para muitas pessoas agora custaria semanas — para zero usuário adicional. A saída madura é a que os times de engenharia usam há décadas: um ADR (Architecture Decision Record, registro de decisão de arquitetura) — um documento curto que registra o que foi decidido, o que foi rejeitado e por quê.

An audit of the project (August 13, 2026) flagged a narrative risk: calling the Bancada a "platform" without being able to explain how it would grow can sound like an empty promise in an interview. Building the many-people version now would cost weeks — for zero additional users. The mature way out is what engineering teams have used for decades: an ADR (Architecture Decision Record) — a short document recording what was decided, what was rejected, and why.

O que muda daqui pra frente

No produto, nada — nenhuma linha de código muda por causa desta decisão. O que muda é que agora existe uma lista de seis regras de construção (os "invariantes") que qualquer mudança futura precisa respeitar para que a migração continue barata: por exemplo, as regras de fluxo de trabalho ficam guardadas como dados numa tabela, e cada anotação registra qual versão das instruções estava valendo quando ela foi feita. Enquanto essas seis regras valerem, trocar o banco local por um servidor é um projeto previsível, não uma reescrita.

In the product, nothing — no line of code changes because of this decision. What changes is that there is now a list of six construction rules (the "invariants") that any future change must respect so migration stays cheap: for example, workflow rules are stored as data in a table, and each annotation records which version of the instructions was in force when it was made. As long as those six rules hold, swapping the local database for a server is a predictable project, not a rewrite.

O que isto NÃO diz

Este documento não promete que a versão multiusuário será construída, não estima prazo nem custo para ela, e não cobre cobrança, pagamento de anotadores ou detecção de fraude — esses são problemas de outro capítulo. Ele também envelhece: foi escrito contra a versão 7 do banco da Bancada, e uma mudança grande de estrutura pede a revisão da lista de regras.

This document does not promise the multi-user version will be built, does not estimate its schedule or cost, and does not cover billing, annotator payment, or fraud detection — those belong to another chapter. It also ages: it was written against version 7 of the Bancada's database, and a major structural change calls for revisiting the list of rules.
